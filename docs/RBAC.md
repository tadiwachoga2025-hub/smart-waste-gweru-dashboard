# Role-based access control

One React app, five roles, one design system. Every person sees only the screens and data their role allows. The **database rules enforce it**; the UI only reflects it.

| Layer | What it does | Where |
|---|---|---|
| Firebase Authentication | Who you are (email + password) | `src/auth/AuthContext.jsx` |
| Realtime Database `users/{uid}` | Your role, status, explicit grants | see data model |
| Security rules | The real access boundary | `database.rules.json` (generated by `scripts/build-rules.mjs`) |
| React | Menus, screens, buttons per role | `src/lib/rbac.js`, `src/App.jsx` |
| Python engine | AI predictions and routes (Admin SDK, bypasses rules) | `engine.py` |

## Access matrix (as implemented)

| Function | Admin | Officer | Driver | Technician | Citizen |
|---|---|---|---|---|---|
| Manage users and roles | Yes | – | – | – | – |
| Bin monitoring dashboard | Yes | Yes | Assigned bins (in My jobs) | Technical view (Devices) | Public view (Report a problem) |
| AI predictions | Yes | Yes | Assigned jobs | Diagnostics | – |
| Generate optimised routes / Route screen | Grant* | Yes | – | – | – |
| Assign trucks and jobs | Grant* | Yes | – | – | – |
| Update collection status | Grant* | Yes | Assigned jobs | – | – |
| Sensor maintenance | Grant* | Flag faults only | – | Yes | – |
| Submit complaints | Grant* | Review queue | – | – | Yes |
| Operational reports | All | All | Own jobs | Device reports | Own reports |
| Audit logs: Internal (people) | Yes | – | – | – | – |
| Audit logs: External (system) | Yes | Yes | – | – | – |

\* An administrator gets these only when another administrator ticks the grant on their profile (Users screen). They are never automatic. Grantable: `routes.generate`, `jobs.assign`, `jobs.update.all`, `sensors.manage`, `complaints.submit`, `complaints.review`.

## Data model

```
users/{uid}        { name, email, role, status: 'active'|'inactive', grants: { [perm]: true }, phone?, createdAt }
bins/{binId}       existing sensor record (fillLevel, lat, lng, location, prediction, lastUpdated)
publicBins/{binId} { location, lat, lng, band: 'normal'|'high'|'critical' }   written by engine.py
logistics          existing (activeRoute, resources) written by engine.py
trucks/{id}        { label, plate, status: 'available'|'in-service'|'maintenance', createdAt }
jobs/{jobId}       { title, driverUid, driverName, truck, priority: 'normal'|'high'|'urgent', status: 'assigned'|'started'|'completed'|'cancelled',
                     notes?, source: 'ai-route'|'manual', createdBy, createdByName, createdAt, startedAt?, completedAt?,
                     stops: [{ binId, location, lat, lng, fillLevel, prediction, done: false, doneAt? }] }
issues/{id}        { jobId, driverUid, driverName, type: 'inaccessible-bin'|'breakdown'|'other', binId?, note, status: 'open'|'resolved', createdAt, resolvedBy? }
complaints/{id}    { citizenUid, citizenName, type: 'overflowing_bin'|'missed_collection'|'other' (see src/lib/complaints.js), binId?, note, lat, lng, address?, photo? (data URL, <=150KB),
                     status: 'new'|'reviewing'|'assigned'|'resolved'|'rejected', officerNote?, jobId?, createdAt, updatedAt? }
devices/{binId}    { binId, model, firmware?, status: 'active'|'faulty'|'replaced'|'retired', installedAt?, notes? }
maintenance/{id}   { binId, type: 'inspection'|'repair'|'replacement'|'calibration'|'report', note, techUid, techName, createdAt }
audit/{id}         { at, actorUid, actorName, actorRole, action, target, detail }   append-only, admin-read (Internal log)
engineLog/{id}     { at, kind: cycle|training|alert|error|lifecycle, status, detail, metrics?, engine }   engine-written, admin+officer read (External log)
engineStatus       { at, state: live|degraded|error|stopped|..., metrics?, engine }   engine heartbeat, admin+officer read
```

Jobs carry a snapshot of their stops so a driver never reads `/bins`. Officers list drivers with `useList('users', { where: ['role', 'driver'] })` (the rules allow exactly that query). Drivers and citizens read through queries (`useList(path, { where: ['driverUid', uid] })`), which is what the rules require.

## First-time setup

1. Firebase console → Authentication → Sign-in method → enable **Email/Password**.
2. Create the first administrator: Authentication → Add user. Copy their UID, then in Realtime Database add `users/<uid>` = `{ "name": "…", "email": "…", "role": "admin", "status": "active" }`. (Console writes bypass the rules, which is what makes this bootstrap possible.)
3. Publish the rules: Realtime Database → Rules → paste `database.rules.json`, or `firebase deploy --only database`.
4. **ESP32 sensors:** the rules deny anonymous writes. Give the gateway its own Auth user with `role: "device"` (not shown in the UI) and have the firmware sign in, or the sensors will stop reporting. Do this *before* publishing the rules — `.venv/bin/python scripts/provision_device.py` creates the account and the profile, and `docs/DEVICES.md` has the firmware request shape.
5. Re-run `engine.py` once so `publicBins` fills in for the citizen view.

## Known limits (be upfront in the project report)

- **The internal audit log is advisory, not tamper-proof.** Entries are written by the browser after an action, so a determined staff member can skip logging. The rules make every entry honest (the actor's uid, role and name must be their own, time is server-stamped, entries cannot be edited or deleted, residents may only log two actions) but cannot force an entry to exist. Mandatory audit needs Cloud Function triggers on `users`, `jobs` and `complaints`. The **external log** (`engineLog`, `alertLog`) is stronger: only the engine (Admin SDK) can write it, so clients cannot forge or erase training runs, cycles or email history.
- **Administrators cannot edit their own role, status or grants** (enforced by the rules), so granting an operational permission always takes a second administrator. Keep at least two administrators.

- **Deactivating a user** sets `status: 'inactive'`: the app signs them out and every rule rejects them, but their Auth login still exists. Truly disabling it needs the Admin SDK or a Cloud Function.
- **Creating staff accounts** from the browser uses a throwaway second Firebase app so the administrator stays signed in. A Cloud Function is the stronger production design.
- **Photos** are compressed in the browser and stored as data URLs in the database to avoid needing Firebase Storage billing. Fine for a prototype; move to Storage at scale.
- `engine.py` uses the Admin SDK and so bypasses rules by design. It is not exposed over HTTP, so there is no server-side authorization surface to protect yet. If you later wrap it in an API, verify the caller's ID token and role there.
- Driver job stops are a snapshot; fill levels in "My jobs" are as of assignment.

## Adding a screen

1. Add a nav entry in `ALL_NAV` (`src/lib/rbac.js`) with the permissions that unlock it.
2. Add the view to `VIEWS` in `src/App.jsx`.
3. If it reads a new path, add the rule in `scripts/build-rules.mjs` and regenerate.
4. Build from `src/components/ui` and `src/styles/ui.css`. Do not restyle primitives.
